Multitenant RAG System
with Semantic Caching

A production-oriented, multitenant retrieval-augmented generation platform — built to keep tenant data isolated while staying fast and relevant under hybrid retrieval.

hero project Python · FastAPI PostgreSQL · pgvector Redis · Docker

The problem

Retrieval-augmented generation gets significantly harder once more than one tenant shares the same system. Every retrieval path has to guarantee that one tenant's documents can never leak into another tenant's answers — while retrieval still has to stay fast and relevant enough to be worth using.

The goal of this project was to build that platform properly: isolation as a first-class constraint, hybrid retrieval for relevance, and a real evaluation loop instead of eyeballing outputs.

What it does

  • Serves retrieval-augmented answers to multiple tenants from one shared platform
  • Isolates tenant data at the SQL layer, not just in application logic
  • Combines sparse (BM25) and dense (pgvector) retrieval for relevance
  • Evaluates retrieval and answer quality with RAGAS, not just manual checks

Engineering decisions

  • Hybrid retrieval (BM25 + dense) instead of dense-only, to catch exact-keyword matches dense embeddings can miss
  • Reciprocal Rank Fusion to merge sparse and dense candidate rankings before reranking
  • Cross-encoder reranking as a precision pass on the fused shortlist, rather than relying on the retriever's ranking alone
  • Redis semantic caching to avoid re-running the full pipeline for near-duplicate queries

Why it matters

Each stage is a separate, swappable piece — retrieval, fusion, reranking, and generation aren't collapsed into one opaque call. That makes it possible to evaluate and tune each stage independently, which is what the RAGAS evaluation loop is built around.

Multitenancy & isolation

  • Tenant isolation enforced at the SQL layer, not just filtered in application code
  • Cross-tenant data leakage prevented across every retrieval path, including hybrid search
  • Retrieval, caching, and generation all respect the same tenant boundary

Why SQL-layer isolation

Enforcing isolation in the database layer means a bug in application logic can't accidentally expose another tenant's documents — the boundary is guaranteed closer to the data, not just trusted to be respected by every code path that touches it.
